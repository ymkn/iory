# IORY design

## 1. 設計の中心

IORY の設計は、次の 3 本柱で判断する。

1. **単一ファイルに集中できること**
2. **本文を失いにくいこと**
3. **UI が静かであること**

この設計文書は、構造図ではなく「なぜそうするか」を残す。

## 2. いまの設計方針

### 2.1 単一ファイル pivot は意図的である
- 初期の workspace / tree ベース設計は、書く行為より管理行為を前面に出しやすい。
- 現在の主体は「いま開いている 1 ファイル」であり、開く導線は native dialog と recent files で足りる。
- したがって UI の主レイアウトは、ファイル管理ツールではなく執筆面として設計する。

### 2.2 ローカル履歴は補助、本文が本体
- 履歴は安心感を高めるが、真実の本文はディスク上のファイルである。
- 履歴は path 単位のローカル snapshot とし、本文を別物にしない。
- restore は「再生」ではなく「巻き戻し」であり、新しい snapshot を残したまま曖昧にしない。

### 2.3 UI は少ないほどよい
- Border や太字で意味を伝え始めると、全体がうるさくなる。
- IORY では、強調よりも余白・整列・位置・抑えた色差で意味を出す。
- 説明文は最後の手段であり、ラベルと配置だけで理解できる状態を優先する。

## 3. 画面設計の原則

### 3.1 Empty state
- 目的は「次に書き始める行動」だけを支援すること。
- 必要なのはロゴ、`New File`、`Open File`、`Recent files` のみ。
- 空状態でアプリの思想を文章で説明しない。

### 3.2 Writing view
- 中央は本文に専念する。
- 左ペインは現在の文書コンテキスト、右ペインは時間的な巻き戻しコンテキストとして分ける。
- それにより、現在把握と履歴把握が混線しない。

現在の責務分離:
- 左: `current` / `document` / `recent files`
- 右: `checkpoint timeline`

### 3.3 通知と状態表示
- 成功通知は一時的でよい。居座らせない。
- 失敗や conflict はユーザー判断が必要なので残す。
- 通知領域は目立つ箱ではなく、画面上部の静かなテキストで十分。

## 4. 保存と履歴の設計判断

### 4.1 autosave
- autosave はユーザーの負担を減らすためのもので、存在感を出しすぎない。
- 保存状態表示は必要だが、執筆体験の中心に置かない。

### 4.2 manual save
- Ctrl+S には意味を残す。
- それは単なる再保存ではなく、「いまの状態を意図的に区切る」行為として扱う。
- したがって、保存成功後に明示 checkpoint を付与するのが筋である。

### 4.3 periodic checkpoint
- 定期 checkpoint は安心感のためにあるが、変化がないのに増えると timeline の意味が薄れる。
- よって、内容が変わったときだけ積む。
- `5分ごと` はデフォルトであり、書き手のリズムに合わせて設定変更可能でよい。

### 4.4 restore semantics
- restore は「いったん preview で見て、納得したら巻き戻す」流れが自然。
- restore 後に newer history を残すと timeline の意味が壊れるので、以後の snapshot は切り捨てる。

## 5. conflict 設計
- clean 状態なら外部変更を取り込める。
- dirty 状態で自動マージを狙うより、壊さず止まる方が正しい。
- conflict UI の目的は説明の多さではなく、選択肢の明確さである。

## 6. Windows / IME / lifecycle の設計姿勢
- エディタは見た目の都合で気軽に再マウントしない。
- 再マウント、fullscreen、drag、native dialog、overlay 表示のどれも IME と focus に影響する。
- ブラウザ上で自然でも、Tauri + WebView2 上で自然とは限らないため、Windows 実機基準で考える。

## 7. 将来機能の入れ方
- LLM、BGM、統計強化などを足すとしても、本文編集より前面に出さない。
- 常設 UI を増やすより、必要時だけ現れる静かな補助として設計する。
- 新機能が保存安全性や IME 安定性を脅かすなら、後回しにする。

## 8. いま残っている設計的負債
- 旧 workspace 前提の名残は、実装上の整理候補である。
- ただし整理でも、いま安定している保存・切替・IME フローを壊してはいけない。
- 見た目の一貫性は今後も継続課題だが、派手な UI を戻す方向ではなく、さらに削る方向で判断する。
