# IORY requirements

## 1. 製品の立ち位置

IORY は、ローカルのテキストファイルを静かに書き続けるための Windows 優先デスクトップアプリである。

このアプリが提供すべき価値は、エディタの多機能さではなく次の 4 点に集約される。

- 余計な UI が視界と判断力を奪わないこと
- 本文ファイルをアプリに閉じ込めず、手元のファイルとして保てること
- 自動保存とローカル履歴で「書いたものが消えにくい」こと
- Windows / IME / native dialog を含めて、日常使用に耐えること

## 2. プロダクトの基本姿勢

### 2.1 単一ファイル中心
- MVP 以降の基準となる体験は **単一ファイル編集** である。
- 起点は `New File` と `Open File`、および最近開いたファイルへの復帰である。
- 「作品 = フォルダ」という前提には戻さない。将来フォルダ機能を足すなら、執筆体験に対する明確な利益が必要。

### 2.2 ユーザーがファイルを所有する
- 編集対象は `.md` / `.markdown` / `.txt` とする。
- 本文は常にユーザーのローカルファイルであり、アプリ独自形式を中心に据えない。
- 履歴や設定はアプリが持ってよいが、それはあくまで補助情報である。

### 2.3 保存を意識させないが、意味は失わせない
- autosave はデフォルト挙動とする。
- ただし「保存した」という明示操作の意味は残す。Ctrl+S は明示的な checkpoint を伴う行為として扱う。
- ユーザーにとっての安心感は、「保存ボタンがあること」ではなく「失われにくいこと」から来る。

## 3. 体験要件

### 3.1 初期画面 / 復帰導線
- 空状態は最小限でよい。ロゴ、`New File`、`Open File`、`Recent files` があれば十分。
- スプラッシュも同じロゴと言語で揃え、説明を増やさない。
- 再起動時は最近のファイルへ自然に復帰できることを重視する。

### 3.2 執筆画面
- 中央は本文、周辺 UI は補助に徹する。
- 左ペインは `current`、`document`、`recent files`。
- 右ペインは `checkpoint timeline` のみ。
- Focus / fullscreen 時も、本文への復帰が自然であること。

### 3.3 見た目の原則
- ミニマルでシンプルであること。
- 装飾的な border、border カード、強調のための bold はデフォルトで使わない。
- 文字説明は必要最小限にする。
- 状態表示は box で叫ばず、静かな位置・余白・色差で伝える。
- ラベル / 値は上下に積み、値は自分の行でのみ右揃えにする。

### 3.4 通知の原則
- 成功や情報通知は控えめに表示され、数秒で消える。
- エラーや conflict は自動で消さず、ユーザーが判断できる状態を保つ。

## 4. 保存・履歴要件

### 4.1 autosave
- autosave は既定で有効。
- デフォルトは 1000ms 程度の短い待機で、保存を意識させない。
- blur やファイル切替時も、本文を落とさない方向で扱う。

### 4.2 local checkpoint history
- 履歴はローカル snapshot として持つ。
- 履歴は path 単位で紐づく。
- 定期 checkpoint のデフォルトは 5 分。
- 内容・encoding・BOM に変化がなければ checkpoint は増やさない。
- Ctrl+S は保存成功後に明示 checkpoint を作る。ただし重複 snapshot は作らない。

### 4.3 restore
- checkpoint restore は「その時点へ巻き戻す」操作として明確であること。
- restore はディスクへ書き戻し、以後のローカル履歴を切り捨てる。
- したがって UI と文言は軽くしつつも、意味は曖昧にしない。

### 4.4 conflict handling
- 外部変更があり、ローカルが clean なら自動再読込してよい。
- ローカルが dirty なら、自動マージしない。
- conflict は「黙って直す」より「壊さず止まる」ことを優先する。

## 5. 非機能要件
- Windows で自然に使えること
- IME 入力、変換、確定、改行が安定していること
- titlebar / fullscreen / overlay を含めて入力フローが破綻しないこと
- 保存ミスやファイル破損を起こしにくいこと
- packaged build を前提に品質確認できること

## 6. 非目標
現時点では以下を中心機能にしない。

- workspace / project 管理中心の UX
- アプリ独自の本文フォーマット
- 派手な装飾 UI
- リッチテキスト編集
- クラウド同期
- LLM / BGM の本実装

## 7. 今後の拡張余地
- LLM や補助機能を足すとしても、本文と保存安全性を最優先とする。
- 新機能は「書くことの妨げにならない overlay」として考える。
- 本文ファイルと補助データの境界は今後も明確に保つ。
